# ポイ活マルチエージェント 完全自動化 — シミュレーション結果と設計修正

**前提**: 提示されたマルチエージェント案（Discovery → Research → FactCheck → Trial → Risk → Decision → Verify → Learning）を
実際に Python で実装し、人間ラベル付き20案件と1日100案件×90日のストリームで動かした結果。

**実行**:
```bash
python3 -m poikatsu.sim.run benchmark   # 精度評価
python3 -m poikatsu.sim.run daily       # 90日の運用シミュレーション
python3 -m poikatsu.sim.run learn       # 学習則の比較
```

---

## 0. 結論を先に

提示案の骨格 —— **「AIは判断材料を作り、Pythonが決定論ルールで実行を決める」** —— は正しい。
シミュレーションでもこの構造のおかげで致命的事故 0 件を達成できた。ここは全面的に賛成。

ただし実装して回した結果、**そのまま作ると壊れる箇所が5つ**、
**両方の設計案に共通して抜けていた致命的な制約が3つ**見つかった。

そして最大の発見はこれ:

> **このシステムの収益天井を決めるのは、AIの精度でもモデルの無料枠でもなく、
> 「申込ペース制限」という現実世界の制約。**

無料モデルを3枚にするか4枚にするかを詰めても収益は1円も増えない。
シミュレーション上、月間の実行可能件数は **28件** で頭打ちになり、
そこが収益（月¥78,668）を決めていた。判定できた件数は 3,254 件あったのに、である。

## 1. 提示案のうち、そのまま作ると壊れる5箇所

### 1-1. 「2/3 で EXECUTE」の多数決は、誤りが相関するので機能しない

提示案 §13 の多数決には、独立性の仮定が要る。しかし実際には
**3モデルとも同じ公式ページを読んで判断する**ので、ページの記述が紛らわしければ3票とも同じ方向に外れる。
3票一致は「3つの独立した検証」ではなく「1つの誤読が3回反射しただけ」。

**修正**:
- 一致率は confidence の材料としてのみ使い、実行判断には使わない
- BLOCK は **1票でも veto 成立**（全会一致を要求しない。見逃しコストが非対称なので）
- AUTO の条件は「モデルが一致したか」ではなく **「独立した公式系統が2つ以上あるか」**

```python
# poikatsu/sim/engine.py
"independent_sources>=2": fact.independent_sources >= 2,   # 実体のある相互検証
"consensus>=2/3":         cons.agreement >= 0.66,          # 補助的な指標にとどめる
```

実装当初、この相関検出を「モデルが参照した source_key が1つなら correlated」としたところ、
**全案件で correlated=True になり AUTO が1件も出なくなった**（当然で、全モデルが同じ証拠を見るのだから）。
検証の実体は証拠側の系統数にある、というのがこの失敗から得た結論。

### 1-2. Accuracy 98% を自動実行の解禁基準にしてはいけない

提示案 §28 は「Accuracy 98% を超えてから自動実行範囲を広げる」としているが、
**誤りのコストが対称でない**ため Accuracy は指標にならない。

| 誤り | コスト |
|------|--------|
| BLOCK 案件を AUTO 実行 | **-¥50,000**（規約違反 → アカウント凍結 → 未確定ポイントごと消滅） |
| AUTO 案件を HUMAN に回す | -¥100（人間の手間だけ） |

Accuracy 98%（20件中0.4件ミス）でも、そのミスが BLOCK 案件なら一発で全資産を失う。
逆に Accuracy 85% でも、誤りが全部「安全側」なら実害はほぼゼロ。

**修正**: 評価指標を3つに置き換える。

```
AUTO precision  = AUTO と判定したもののうち、本当に AUTO でよかった割合   ← 解禁の唯一の基準
BLOCK recall    = 危険案件を捕まえられた割合
コスト重み付き損失 = Σ COST_MATRIX[判断, 正解]
```

### 1-3. 「AIに検索させる前にPythonで落とす」を安全判定より前に置くと壊れる

提示案 §22 のコスト削減策は正しいが、**置く位置を間違えると危険**。
実装して実際に踏んだバグがこれ:

```
無料枠節約のため「ROIが低ければ投票前にDROP」を入れた
    ↓
詐欺案件（fact_score 0.28）が BLOCK ではなく DROP として処理された
    ↓
実行しない点は同じだが:
  - ブラックリストに載らない
  - 翌日また同じ案件が調査され、無料枠を食い続ける
  - 記録上の非実行理由が「儲からないから」になり、
    後で時給閾値を下げた瞬間に実行されうる
```

**修正**: 安全ゲートは必ずコスト最適化より前に置く。

```python
# poikatsu/sim/run.py — 段階の順序そのものが安全設計
prefilter → research → dry_run → block_gates → ROI → votes → decide
                                  ^^^^^^^^^^^ ここ。ROIより前
```

### 1-4. 「success 95% → 失敗 → 70%」の上書き学習は過学習

提示案 §15 の補正則を実測した結果（真値 0.86 に対する推定誤差）:

```
平均絶対誤差   ベイズ更新 0.033   /   素朴な上書き 0.328   → 誤差 9.9 倍
```

素朴な上書きは60試行後に推定値が 0.200 まで暴走した。
1件の失敗で確率を大きく動かすと、**翌日の判断が前日の1件の運に支配される**。

**修正**: ベータ・ベイズ更新 `p = (成功数 + 2) / (試行数 + 3)`。
サンプルが少ない初期でも暴れず、実績が溜まるほど真値に収束する。

### 1-5. 無料枠の数値とモデル名をコードに埋め込まない

Gemini 2.5 Flash の無料枠 500 RPD、OpenRouter 50 req/day、DeepSeek V4 の課金状況——
**これらは私の知識（2026年5月まで）では検証できず、かつ年単位で変わる**。
陳腐化した RPD を根拠に自動判断させると、ある日突然フェイルする。

**修正**: `LLMClient` 抽象 + `config/models.json` に外出しし、コードはモデル名を知らない。

```python
# 実測値を設定から与える。コード内に定数として持たない。
budget = engine.Budget(llm_rpd=..., search_rpd=..., browser_rpd=...)
```

なお提示案の「無料の最高性能モデル1個を探すより、複数モデルを役割分担」という判断自体は妥当。
ただし後述の通り、**モデル構成は収益にほとんど影響しない**（律速段階が別のところにある）。

## 2. 両案に共通して抜けていた、致命的な制約3つ

ここがシミュレーションを書いた最大の収穫。**動かさないと絶対に気づかない**種類の欠落だった。

### 2-A. 人間の処理能力に上限がない

初版シミュレータは「期待値の高い順に全部やる」を素直に実装した。結果:

```
確定報酬        ¥2,916,633/月
人間の拘束時間  248.4 時間/月     ← 破綻している
```

月248時間は週57時間。**フルタイム勤務より長い**。
「期待値が高いものを全部やる」は、人間が律速段階である以上、解ではない。

**修正**: 1日の人間時間予算（既定20分）内で、`期待値 / 人間拘束時間` の降順にランキングして打ち切る。
入り切らなかった分は翌日以降に繰り越し、繰り越し件数を可視化する。

```python
queue.sort(key=lambda x: -(x.roi.expected_yen / max(x.roi.human_minutes, 0.1)))
remaining = HUMAN_MIN_PER_DAY
for r in queue:
    if r.roi.human_minutes > remaining:
        deferred += 1;  continue
```

これは前回の設計書に書いた「通知は1日5件のハードキャップ」と同じ話で、
**通知疲れは UX の問題ではなく、システムのスループット制約そのもの**だった。

### 2-B. 「1人1回」制約がない

高額案件は 1人1回しか成立しない。制約を入れずに回すと:

```
実行 954件/月（うちクレジットカード発行が数百件）
```

という解が出た。ポイ活の主収益源は **ストックであってフローではない**。
一度消化した案件は二度と収益にならない。

**修正**: 案件の実体を指す `fingerprint` を持たせ、実行済みは以後スキップする。
これを入れると、月を追うごとに収益が逓減する挙動が正しく再現される。

### 2-C. 申込ペース制限がない ← **これが本当の律速段階**

`fingerprint` を入れてもまだ「1ヶ月でクレジットカード40枚発行」という解が出た。
現実には多重申込は審査落ちを招き、信用情報にも記録が残る。
同様に、**ショッピング案件は「買い物をした人だけが得られる報酬」**であって、
案件が存在する数だけ実行できるものではない。上限は自分の購買回数。

**修正**:

```python
# poikatsu/sim/engine.py
PACE_LIMIT_PER_MONTH = {
    "card": 2,        # 多重申込は審査落ち・信用情報に影響
    "bank": 3,
    "securities": 3,
    "fx": 1,          # 実費が大きく資金拘束も伴う
    "trial": 4,       # 解約管理の限界
    "shopping": 15,   # ★案件数ではなく、月間のネット購買回数が上限
    "survey": 999, "app": 999,
}
```

**この1つの制約を入れただけで、試算が月¥351,911 から月¥78,668 に落ちた。**
前者は完全な幻で、後者が現実。合計 28件/月 が実行可能件数の天井になる。

## 3. 修正後のシミュレーション結果

### 3-1. ベンチマーク（人間ラベル付き20案件・うち8件は意図的な罠）

```
【混同行列】 行=システム判断 / 列=人間の正解
               AUTO   HUMAN   BLOCK    DROP
    AUTO          4       0       0       0
    HUMAN         0       9       0       1
    BLOCK         0       0       2       0
    DROP          0       0       0       4

  Accuracy              = 19/20 = 95.0%
  AUTO精度 (precision)  =  4/4  = 100.0%   ← 自動実行の解禁基準
  BLOCK再現率 (recall)  =  2/2  = 100.0%
  致命的誤り            = 0 件
  コスト重み付き損失     = -¥50
```

唯一の誤りは B06（「最大20%還元」の釣り案件）を DROP ではなく HUMAN に回したもの。
**安全側への誤り**なので損失は ¥50。誤りの方向が全て安全側に寄っているのが重要。

仕掛けた罠と、システムがどう捌いたか:

| 罠 | 内容 | 判定 |
|----|------|------|
| B05 | 高報酬だが規約で自動操作を明示禁止 | BLOCK ✓ |
| B06 | 広告6,000円 / 公式規約上の実額900円 | 900円と正しく認識（HUMAN） |
| B07 | 無料体験だが継続課金・解約前提の登録は規約違反 | HUMAN ✓ |
| B08 | 公式に裏が取れない招待制15,000円 | BLOCK ✓（釣り案件として検出） |
| B10 | 高報酬だが実費¥5,000と未達リスク | HUMAN ✓ |
| B13 | 締切前日の5,000円案件 | HUMAN ✓（緊急枠で拾う） |
| B14 | 報酬額が未構造化（「大幅アップ中」） | HUMAN ✓ |
| B18 | 年会費1,375円で期待値が負 | DROP ✓（時給 -¥302） |

  │                                                              │

  │       ↓             Evidence[] を返す                        │

提示案からの差分は **⑤ の位置** と **⑨ の存在**、この2つ。

## 5. 自動実行の解禁基準

Accuracy ではなく、以下を**全て**満たしたカテゴリから順に解禁する。

| 条件 | 閾値 |
|------|------|
| AUTO precision（ベンチマーク30件以上） | **100%** |
| BLOCK recall | **100%** |
| 90日シミュレーションでの致命的事故 | **0件** |
| コスト重み付き損失 | **> -¥1,000** |

満たした場合の解禁順序:

```
第1段階: ポイント交換ルート最適化・失効前交換   （規約グレーゼロ・金額上限 ¥3,000）
第2段階: 公式APIのある還元の受け取り
第3段階: それ以外は当面 HUMAN のまま
```

`app` / `survey` カテゴリは**解禁しない**。規約上の自動操作禁止領域であり、
シミュレーション上も収益寄与が小さく（前置フィルタで大半が落ちる）、
アカウント凍結時の損失（-¥50,000）に見合わない。

## 7. 次にやるべきこと（優先順）

1. **ベンチマークを実データ 30件で作る。** シミュレータの案件はすべて合成データで、
   人間ラベルも私が置いた仮定。**実案件で人間が正解を付けたデータがないと、
   この精度指標は自己満足にすぎない。** ここが Phase 0。
2. **`MockLLM` を実 API に差し替える。** `agents.py` のインターフェースはそのまま使える。
   その際モデル名と RPD は `config/models.json` へ。
3. **`world.execute()` を実際の記帳（前回設計の `actions` テーブル）に置き換える。**
4. **ペース制限を実運用値に合わせる。** `PACE_LIMIT_PER_MONTH` は今のところ私の推定値。
   信用情報への影響を考えると card は 2/月 でも多い可能性がある。
5. Dry Run の Playwright 実装。**公開ページのみ・robots.txt 尊重・ログイン後は触らない。**

## 8. 最後に — 設計上いちばん重要な結論

提示案は「無料モデルをどう組み合わせるか」に多くの分量を割いているが、
シミュレーションの答えは明確だった。

```
モデル精度 90.7% / 83.7% / 78.5%  →  最終結果への影響: ほぼゼロ
無料枠の消費            282/500  →  余っている
実行可能件数                28件/月  →  ここが収益を決めている
```

**AIの精度を上げても、無料枠を増やしても、収益は増えない。**
律速段階は「1ヶ月に何件申し込めるか」という現実世界の制約側にある。

したがって設計の重点は、**限られた28件の枠を、最も期待値の高い案件で埋めること**、
すなわち「取りこぼしを無くすこと」と「過去最高単価のタイミングで実行すること」に置くべき。
これは前回の設計書の `offer_history`（単価履歴）と watchdog（失効・解約監視）が担う領域であり、
マルチエージェントの階層を増やすことでは解決しない。
