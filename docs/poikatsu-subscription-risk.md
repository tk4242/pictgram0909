# 継続課金案件の解約忘れリスク — 実測と対策設計

**問い**: 「初月無料、継続で有料」の申込案件は解約を忘れるリスクがないか?

**答え**: **ある。しかも対策なしだと報酬より損失の方が大きい。**

```bash
python3 -m poikatsu.sim.run cancel
```

---

## 1. 実測結果

無料体験案件を48件（月1件ペース＝4年ぶん）処理したときの収支。400試行の平均。

| 管理方式 | 着手 | 報酬 | 漏れた課金 | **純利益** | 忘れ率 |
|---------|-----|------|-----------|----------|-------|
| ① 管理なし（手動） | 48 | ¥114,888 | ¥123,819 | **-¥8,931** | 40.9% |
| ② 期限3日前に1回通知 | 48 | ¥114,888 | ¥45,462 | ¥69,426 | 15.1% |
| ③ 多段エスカレーション通知 | 48 | ¥114,888 | ¥16,827 | **¥98,060** | 5.5% |
| ④ ③ + WIP制限（同時2件） | 47 | ¥113,293 | ¥16,675 | ¥96,618 | 5.4% |

**管理なしでは、報酬 ¥114,888 に対して漏れた課金が ¥123,819（報酬の108%）。純利益は赤字。**
やればやるほど損をする領域に入る。

### 忘れ率が 40.9% にもなる理由

基礎的な「忘れる確率」は25%と置いたのに、実測では40.9%まで悪化している。
これは**解約し損ねた案件が、気づくまでの数ヶ月間ずっと「仕掛かり」として居座り、
次の案件を忘れる確率を押し上げる**から。1件の取りこぼしが次の取りこぼしを呼ぶ悪循環になる。

```python
# poikatsu/sim/cancel.py — 忘れる確率は仕掛かり件数で悪化する
def forget_probability(policy, wip):
    return min(0.95, BASE_FORGET[policy] * (1.45 ** (wip - 1)))
```

## 2. WIP制限について（当初の想定は間違っていた）

実装前は「通知を厚くするより同時保有件数を制限する方が効く」と考えていたが、
**データはそれを支持しなかった**。平時では ③→④ で純利益はむしろ微減する（¥98,060 → ¥96,618）。

WIP制限が効くのは、通知が劣化したときだけ。ストレス条件（通知疲れで忘れ率 5%→18%）:

| 管理方式 | 着手 | 純利益 |
|---------|-----|-------|
| ③ 多段通知のみ | 48 | ¥38,658 |
| ④ ③ + WIP制限 | 44 | **¥48,777** |

**着手を48件→44件に絞ってなお ¥10,120 勝つ。**

### 結論

1. **主効果は多段エスカレーション通知。** これだけで赤字→黒字に反転する（-¥8,931 → ¥98,060）
2. **WIP制限は利益を増やす装置ではなく、破綻を防ぐサーキットブレーカー。** 平時は効かないが、
   通知が効かなくなったときに損失を止める。保険として入れる価値がある
3. **管理手段が無いなら、このカテゴリには着手しない方が儲かる**

## 3. 対策の実装設計

### 3-1. 登録した瞬間に解約期限を確定させる

**登録後に手で入力する運用は必ず破綻する。** 登録完了メールから自動生成する。

```python
# collector_gmail.py
# 「登録完了」「お申し込みありがとう」メールを検知した時点で cancel_due を自動生成
cancel_due = registered_at + free_days - SAFETY_MARGIN_DAYS   # 安全マージン3日
```

安全マージンを3日取るのは、**「無料期間30日」の起算日が申込日か課金日かがサービスごとに違う**ため。
月末起算のサービスもある。ここは楽観側に倒さない。

### 3-2. 多段エスカレーション通知（主効果）

| タイミング | 内容 |
|-----------|------|
| 期限30日前 | 一覧に載せるのみ（通知しない） |
| 期限7日前 | 通常通知 |
| 期限3日前 | 🚨 最優先通知 + 解約手順URL |
| 期限前日 | 🚨 通知 + 他の全通知を抑制（これだけ出す） |
| 期限当日 | 🚨 通知を1時間おき（解約完了メールを検知するまで） |
| **期限超過** | 🔴 「課金が始まっている可能性」として毎日通知 + 新規trial案件の受付を停止 |

**期限超過後も通知を出し続けるのが重要。** 忘れた案件は平均4ヶ月気づかれない、というのが
損失の本体だから、「気づくまでの時間」を短縮するだけで損失は比例して減る。

### 3-3. 解約完了をメールで確認するまでクローズしない

```python
# 状態遷移。「解約したつもり」で閉じない
registered → cancel_scheduled → cancel_requested → cancel_confirmed
                                                    ^^^^^^^^^^^^^^^^
                                     解約完了メールをパースして初めてここ
```

自己申告（「解約した」とボタンを押す）でクローズできる設計にすると、
**押したのに解約できていなかったケース**を検出できない。

### 3-4. WIP制限（サーキットブレーカー）

```python
WIP_LIMIT = 2   # 未クローズの継続課金案件を同時に2件まで
# 上限に達している間は、新規の trial 案件を candidate 段階で自動的に見送る
```

前段の設計書（`poikatsu-multiagent-simulation.md`）の `PACE_LIMIT_PER_MONTH["trial"] = 4` とは別の制約。
あちらは月間フロー、こちらは同時ストックの制限。**両方要る。**

### 3-5. 管理できない案件は最初から BLOCK

すでにマルチエージェント側の安全ゲートに実装済み:

```python
# poikatsu/sim/engine.py
if trial.recurring and not trial.observable:
    return Decision("BLOCK", "継続課金だが解約条件を公開情報で確認できない")
```

**解約方法が公開ページで確認できない継続課金案件には着手しない。**
「電話でしか解約できない」「解約導線がログイン後にしかない」ものは、
報酬がいくら高くても期待値が負になりうる。

## 4. 実運用での注意

- **解約前提の登録を禁止しているサービスがある。** 規約を確認し、禁止されている場合は着手しない。
  この場合、報酬を受け取ったうえで即解約する行為自体が規約違反になる
- 継続課金案件は本設計では常に **HUMAN 判定**（自動実行しない）。
  支出が発生する意思決定を自動化しないため
- 上記の数値モデル（忘れる確率25%、気づくまで平均4ヶ月、WIPペナルティ1.45倍）は
  すべて**私が置いた仮定**。実運用の実績が溜まったら実測値に置き換えること
