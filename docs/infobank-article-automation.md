# InfoBank 記事作成 自動化・半自動化 検討レポート

対象サイト: [InfoBank（ベトナム経済情報サイト）](https://infobank-vn.com/)
作成日: 2026-08-12

---

## 1. 結論（先に3行）

1. **Claude Code で完結できます。** 本文・タイトル・メタディスクリプション・グラフ・サムネイル・WordPress入稿まで、すべて1つのパイプラインに収まります。
2. **ChatGPT の画像生成は不要です。** 求められているのは「pptxテンプレートに沿ったグラフ・図表」であり、これは画像生成AIではなく `python-pptx` によるテンプレート流し込みが正解です（画像生成AIは日本語の文字と数値を正確に描けません）。
3. **VPS は必須ではありません。** 最終チェックが人間である以上、完全無人稼働の価値は限定的です。ただし後述の「NNAログインの固定IP維持」という理由で、第3段階では有用です。

**最大の論点は技術ではなく、NNA記事の二次利用が契約上許されるかです（第6章 リスク①）。ここだけは着手前にクライアント確認が必要です。**

## 3. ご質問への回答

### 3.1 Claude Code で完結するか → **できます**

各フェーズの担当は以下の通りです。

| フェーズ | 担当 | 備考 |
|---|---|---|
| 元記事の要約・論点抽出 | Claude | |
| 現地語（ベトナム語・英語）ソースの探索 | Claude + Web検索ツール | Notionの推奨プロンプトそのもの |
| 「＋α」の背景リサーチ | Claude + Web検索 | 過去の展開まとめ、法改正の背景など |
| 本文執筆（1,500字・H2構成） | Claude | |
| タイトル26〜28文字の複数案生成 | Claude ＋**文字数バリデータ（コード）** | 日本語の文字数制約はAIに任せず機械で検証 |
| メタディスクリプション80〜90文字 | 同上 | |
| グラフ・図表の pptx 生成 | **python-pptx**（Claudeがコード実行） | テンプレートを直接編集するのでトンマナが100%一致 |
| pptx → PNG 変換（WP貼付用） | LibreOffice headless | |
| サムネイル生成 | HTML/CSS → Playwright でPNG化、または Canva | 本環境にChromium導入済み |
| 現地メディア画像の高解像度化 | magnific API | |
| Notion納品（テスト段階） | Notion API | |
| WordPress下書き投稿 | **WP REST API** | 後述の通り利用可能を実機確認済み |

**Claude Code 単体で足りないのは「スケジュール実行」だけです。** これは以下のいずれかで解決します。

- 手動運用（推奨・初期）… 1日1回まとめてURLを投入
- GitHub Actions の cron … サーバー管理不要・ほぼ無料
- VPS常駐 … NNAへのログインIPを固定したい場合に有利
- Claude Managed Agents のスケジュール実行 … サーバー管理不要でサンドボックス付き

### 3.2 ChatGPT（画像生成）を併用すべきか → **不要です**

理由を整理します。

**求められているのは「作画」ではなく「テンプレートへのデータ流し込み」です。**
支給されている `グラフ・図表作成のテンプレート_0602.pptx` に、キーメッセージと図表タイトルとデータを入れる作業です。ここで画像生成AIを使うと、

- 日本語のラベルが崩れる／読めない文字になる
- グラフの数値が実データと一致しない（＝事実誤認そのもの）
- 「過去記事のトンマナに合わせる」要件を満たせない
- pptx形式で納品できない（画像しか出ない）

という4点で要件を満たせません。`python-pptx` でテンプレートのプレースホルダを差し替える方式なら、トンマナは定義上100%一致し、pptxのまま納品でき、数値もデータソースから機械的に転記されるので捏造が起きません。

**サムネイルも同様です。** 「デザインの変更の必要は無し、文字と色味だけ変更」という要件は、まさにテンプレート差し替えです。3パターンをHTML/CSSで再現してPNG化する方式が、最も安定して速い（1枚1秒未満、完全に決定論的）です。Canva Pro の一括作成（Bulk Create）機能でCSVから量産する方法もあり、こちらはCanva上のデザイン資産をそのまま使える利点があります。

**唯一、画像生成AIが候補になり得るのは「記事のイメージ画像が欲しいが現地メディア画像を使えない場合」です。** ただし報道系メディアで生成AI画像を使うのは信頼性の観点で推奨しません。現地メディア画像＋magnificでの高解像度化、で足ります。

### 3.3 Python + VPS で半自動・自動化できるか → **できます。ただし段階的に**

技術的には全自動化可能ですが、**「最終チェックは人間」という前提がある以上、下書き生成までを自動化し、公開ボタンは人が押す設計**が最適です。ここを踏み外すと、事実誤認記事が自動公開される事故が起きます。

実機で確認した対象サイトの技術構成は以下の通りで、自動入稿の条件は揃っています。

| 確認項目 | 結果 |
|---|---|
| WordPress REST API (`/wp-json/wp/v2/`) | **稼働中** |
| Application Passwords（API認証） | **有効**（`/wp-admin/authorize-application.php`） |
| xmlrpc.php | 403（無効化済み。REST APIを使うので問題なし） |
| テーマ | Emanon |
| 会員限定機能 | WP-Members ＋ Content Control プラグイン |
| カテゴリ | 30件（経済15、食品・外食15、卸・小売9…）※ID取得済み |
| タグ | 100件以上（ニュース解説16、インタビュー11、特集10…）※ID取得済み |

カテゴリ・タグのIDは既に取得できているため、**記事内容からの自動分類・自動タグ付けが可能**です。

### 3.4 実行主体の役割分担（重要な補足）

「Claude Codeで完結する」は**ベンダーを増やす必要がない**という意味であり、「Claude Codeを24時間VPSに常駐させる」という意味ではありません。ここは混同しやすいので明示します。

| 主体 | 役割 | 稼働タイミング |
|---|---|---|
| **Claude Code** | このシステムを**作る**（設計・実装・修正・テスト・VPS設定）。運用開始後もプロンプト改善やトンマナ調整で使う | 開発時・保守時 |
| **Claude API** | 本番で**記事を作る**（リサーチ・執筆・レビュー） | 毎回の記事生成 |
| **Python** | オーケストレーター。いつ・何を・どの順で実行し、成果物をどう保存・入稿するか | 常時 |
| **VPS / GitHub Actions** | 実行基盤（Phase 3・任意） | 定時 |

つまり **Claude Code = 開発者役、Claude API = 実行役** です。同じAnthropicの技術なのでベンダーは1社で済み、追加の外部サービスは不要、というのがQ1の回答の趣旨です。

なお、Claude Code のヘッドレス実行（`claude -p`）や Claude Agent SDK を使えば、Claude Code 自体をバッチ実行の主体にすることも技術的には可能です。ただし**本番運用は Python + Claude API のほうが安定し、デバッグもコスト管理も容易**なので、上記の分担を推奨します。

## 4. 推奨アーキテクチャ

```
[ NNA記事（本文テキスト）]
          │  ※取得方法は第6章リスク①参照
          ▼
┌─────────────────────────────────────┐
│ ① リサーチ層  Claude + Web検索                        │
│   ・ベトナム語/英語の現地ソース探索                    │
│   ・「＋α」背景情報の収集                              │
│   ・グラフ用データの収集（GSO・税関総局・World Bank等） │
│   → 出力: リサーチJSON（全主張に出所URL付き）          │
└─────────────────────────────────────┘
          ▼
┌─────────────────────────────────────┐
│ ② 執筆層  Claude                                       │
│   ・リード文＋H2構成の本文 1,500字                     │
│   ・タイトル案 5本（26〜28字）／メタディスクリプション  │
│   ・図表2枚分のキーメッセージ＋図表タイトル＋データ     │
│   ・画像キャプション（出所＋リンク付き）                │
│   ・カテゴリ／タグの提案                                │
│   ・会員限定の区切り位置（全体の2/3地点）              │
└─────────────────────────────────────┘
          ▼
┌─────────────────────────────────────┐
│ ③-a 機械検証  Python（AIを介さない合否ゲート）         │
│   ・タイトル文字数 26〜28字か／「ベトナム」を含むか     │
│   ・メタディスクリプション 80〜90字か                  │
│   ・本文が1,500字±15%か／H2が2つ以上あるか            │
│   ・全数値に出所URLが紐づいているか                     │
│   ・図表2枚＋キャプション（出所リンク付き）があるか      │
│   ・元記事とのn-gram重複率（コピーコンテンツ検知）      │
│   → 不合格なら②へ差し戻し（自動リトライ）             │
└─────────────────────────────────────┘
          ▼
┌─────────────────────────────────────┐
│ ③-b AIレビュー層  Claude ×3（別コンテキスト）          │
│   Fact-Checker … 元記事とリサーチJSONだけを見て        │
│                  本文に事実の飛躍がないか探す           │
│   Critic       … 論理構成・読みやすさ・冗長さを批判      │
│   SEO Checker  … H2キーワード、内部リンク候補、         │
│                  過去記事との重複・矛盾                 │
│   → 品質スコアと「要注意箇所」を出力                   │
└─────────────────────────────────────┘
          ▼
┌─────────────────────────────────────┐
│ ④ 生成層  Python                                       │
│   ・python-pptx → 支給テンプレートに図表2枚を生成       │
│   ・LibreOffice headless → pptx を PNG 化              │
│   ・Playwright → サムネイル3パターンを順番に生成        │
│   ・magnific API → 現地メディア画像を高解像度化         │
└─────────────────────────────────────┘
          ▼
┌─────────────────────────────────────┐
│ ⑤ 納品層                                               │
│   テスト段階: Notion API でページ作成                  │
│   本番:       WP REST API で「下書き」投稿             │
│               アイキャッチ・カテゴリ・タグ・            │
│               会員限定タグまで自動設定                  │
│   ＋ ファクトチェックシート（段落↔出所の対応表）       │
└─────────────────────────────────────┘
          ▼
     [ 人間による最終チェック → 公開 ]
```

**この設計の要点は③と、⑤のファクトチェックシートです。**

- **③-a（機械検証）** により、文字数のような機械で検証できる制約をAIの気まぐれに任せません。日本語のタイトル26〜28文字は「ベトナム」（4文字）を除くと実質22〜24文字で、AIは高頻度で外します。機械で検証して自動リトライさせるのが確実です。
- **③-b（AIレビュー）** を執筆と分けているのは、**同じコンテキストで「これで完璧ですか」と聞いても機能しないから**です。AIは自分の出力に引きずられます。元記事とリサーチJSONだけを渡した**まっさらなコンテキストのレビュアー**に「事実の飛躍を探せ」と指示するほうが、検出率が明確に高くなります。Claude Code のサブエージェント機能、または API のマルチエージェント構成で実装します。
- **⑤のファクトチェックシート**は、**「本文の各段落 ↔ その根拠となった元記事の該当箇所／参照URL」の対応表**です。これがあると最終チェックが「ゼロから読み直す」作業から「対応表を照合する」作業に変わり、1記事あたり20〜30分 → 7〜10分に短縮できます。半自動化の効果はここで一番大きく出ます。

### 4.1 品質スコアによるトリアージ

③-a と ③-b の結果を1枚のスコアにまとめ、**チェックの順番と注意箇所を提示する**ために使います。

| 区分 | 項目 | 扱い |
|---|---|---|
| **機械（合否ゲート）** | タイトル26〜28字／「ベトナム」含有 | 不合格＝即差し戻し。点数化しない |
| | メタディスクリプション80〜90字 | 同上 |
| | 本文1,500字±15%／H2が2つ以上 | 同上 |
| | 全数値に出所URLが紐づく | 同上 |
| | 図表2枚＋出所リンク付きキャプション | 同上 |
| | 元記事とのn-gram重複率が閾値未満 | 同上 |
| **AI（優先度づけ）** | 事実の裏取り（Fact-Checker） | 30点 |
| | 論理構成・読みやすさ（Critic） | 25点 |
| | 「＋α」（背景・独自性）の充実 | 20点 |
| | トンマナ一致（過去記事との照合） | 15点 |
| | SEO（H2キーワード・内部リンク候補） | 10点 |

**重要な運用ルール：AIスコアを公開の可否判断に使いません。**

AIの自己採点は一般に甘く、較正されていません。スコアの用途は「今日の3本のうち、どれをどの順で、どこに注意して読むか」を決めることに限定します。出力はこの形にします。

> **本日3件、下書き完了**
> ・記事A 92点 — 特記なし
> ・記事B 85点 — **要注意：第3段落の輸出額（出所がホワイトリスト外）**
> ・記事C 78点 — **要注意：H2「ベトナム 半導体」が過去記事と重複／リード文が冗長**

こうすれば自己採点の甘さがあっても害がなく、**チェックすべき場所が最初から特定されている**ぶんだけ確実に時間が縮みます。

### 4.2 運用ログ（システムを改善し続けるための計測）

記事ごとに以下を記録します。これがないと、プロンプトの改善が勘に頼ることになります。

- 人間が修正した箇所数・修正文字数
- 修正の分類（事実誤り／文体・トンマナ／SEO／図表・データ／その他）
- AIスコアと実際の修正量の乖離（＝スコアの較正に使う）

月次でこれを棚卸しし、頻出パターンをスタイルガイドとプロンプトに反映します。**30〜50本/月というペースなら、2〜3ヶ月で修正率は目に見えて下がります。**

## 5. 段階導入プラン

### Phase 0：トンマナの抽出（所要 2〜3日）

**ここが全体の土台です。** 以下を解析して機械可読な「スタイルガイド」を作ります。

- 過去記事20本程度（文体、リード文の型、H2の付け方、段落の長さ、キャプションの書式）
- 支給pptxテンプレート（プレースホルダ構造、配色、フォント、グラフの型）
- Canvaサムネイル3パターン（配色、フォント、文字配置、ロゴ位置）
- カテゴリ・タグの使い分けルール（実データから抽出）

過去記事の分析は既に一部着手済みで、たとえばキャプションが
「（説明文）（出所）〇〇株式会社「資料名」」
という定型であること、メタディスクリプションが結論先出しで約90字であることなどが確認できています。

### Phase 1：Notion納品まで半自動化（所要 1〜2週間）

上図①〜④＋Notion納品。VPS不要、手元で実行。
**ここまでで工数削減の8割が達成できます。**

### Phase 2：WordPress自動下書き投稿（所要 3〜5日）

Application Password を発行してもらい、REST API で下書き投稿。アイキャッチ画像アップロード、カテゴリ・タグ設定、会員限定の区切り挿入まで。

### Phase 3：定時実行の自動化（任意・所要 2〜3日）

URLをNotionデータベースかスプレッドシートに貯めておき、定時バッチで一括処理。VPS／GitHub Actions／Managed Agents のいずれか。

### 5.1 モジュール構成

層ごとにファイルを分けます。「画像処理だけ別サービスに差し替える」「レビュアーを1本追加する」といった変更が局所で済むようにするためです。

```
pipeline/
  run.py                  # オーケストレーター（Pythonが全体を制御）
  sources/
    nna_input.py          # 記事本文の受け取り（手動投入。リスク①の回避策）
  research.py             # ① リサーチ層（Web検索・現地ソース・データ収集）
  writer.py               # ② 執筆層
  validators.py           # ③-a 機械検証（合否ゲート）
  reviewers/
    fact_checker.py       # ③-b 別コンテキストでの事実照合
    critic.py             # ③-b 論理構成・読みやすさ
    seo_checker.py        # ③-b SEO・過去記事との重複
    score.py              # 品質スコアの集計
  media/
    charts.py             # python-pptx（支給テンプレートに図表生成）
    pptx_to_png.py        # LibreOffice headless
    thumbnail.py          # Playwright（サムネ3パターン）
    upscale.py            # magnific API
  delivery/
    notion.py             # テスト段階の納品
    wordpress.py          # WP REST API（下書き投稿）
    factsheet.py          # ファクトチェックシート生成
  store.py                # SQLite: 記事インデックス・運用ログ
  notify.py               # 完了通知（Slack / Discord / LINE）
  style_guide/            # Phase 0 の成果物（トンマナ定義・過去記事サンプル）
```

**データ保存は SQLite で十分です。** 月50記事なら年間600行程度で、PostgreSQL や Docker を持ち込む必要はありません。VPS上でもファイル1個で完結し、バックアップも `cp` で済みます。将来、複数人が同時に入稿するようになった段階で PostgreSQL への移行を検討すれば足ります。

**通知**は1日1.5〜2.5記事のペースなので、バッチ完了時に「本日◯件、下書き完了。うち◯件は要注意」を1通送るだけで十分です。

## 6. 問題点・リスク（優先度順）

### 🔴 ① NNA記事の二次利用が契約上許されるか（**着手前に要確認**）

NNAは有料購読制のニュース配信サービスです。以下の2点は、技術ではなく契約の問題なので、クライアント側からNNAへ確認していただく必要があります。

1. **NNA記事を元にした記事の商用メディアへの掲載が、購読契約上許されるか。** 事実そのものに著作権はありませんが、記事の構成・表現をなぞると翻案権の侵害になり得ます。Notionの推奨プロンプトに「コピーコンテンツにならないように表現は変更してください」とあるのはこのリスクを意識されてのことと思いますが、契約上の可否は別問題です。
2. **自動取得（スクレイピング）の可否。** 多くの有料ニュースサイトは規約でこれを禁止しています。

**推奨する対応:** 確認が取れるまでは、**NNA記事本文は人が手動でコピー＆ペーストして投入する設計**にします。パイプラインの入口を「URL」ではなく「テキスト」にするだけで、自動ログイン・自動取得を一切行わずに済み、法的リスクを大きく下げられます。工数増は1記事あたり30秒程度で、自動化のメリットはほぼ損なわれません。

### 🟠 ② 現地メディア画像の転載

Notionには「画像は現地メディアが掲載している画像を使用可。但し、出所先と出所リンクは明記すること」とあります。日本の著作権法上、出所明記だけでは足りず、「引用」の要件（主従関係、必然性、明瞭区別性）を満たさない転載は権利者の許諾が必要です。これがクライアントの方針として了承済みの運用なのか、確認しておくことをお勧めします（自動化の設計自体は変わりませんが、把握しておくべき点です）。

### 🟠 ③ WordPress「執筆者（Author）」権限の制約

以下は権限付与後の実機検証が必要です。

- Application Password が Author 権限で発行できるか（サイト側でこの機能自体が有効なのは確認済み）
- 会員限定の区切り設定（WP-Members / Content Control）が REST API 経由で書き込めるか
- アイキャッチ画像のメディアアップロードが Author 権限で可能か（通常は可能）
- 支給資料「会員限定記事の設定方法.pdf」に記載の設定方法が、ショートコードなのかブロックなのかで実装が変わります

現在、記事本文はログイン前提のため REST API 上も非公開（「このコンテンツを表示するにはログインが必要です」）になっており、認証情報を頂いてから確認します。

### 🟡 ④ グラフ用データの調達（品質面の最大の論点）

**元記事だけではグラフ2枚分のデータが揃わないケースが大半です。** イオンモールの記事例でも、企業のIR資料（中期経営計画・決算説明資料）からデータを取っていました。

対策として、**参照可能なデータソースのホワイトリスト**を最初に定義します。

- ベトナム統計総局（GSO）
- ベトナム税関総局（輸出入統計）
- ベトナム中央銀行（SBV）
- World Bank / IMF / ADB
- 上場企業のIR資料（イオン、ホンダ、VinFast等）
- 業界団体レポート

そのうえで、**ホワイトリスト外のソースから取得した数値は自動的に「要確認」フラグを立てる**運用にします。「グラフを2枚作らねばならない」というノルマがAIに数字を作らせる最大の誘因なので、ここは機械的に縛るべきです。

### 🟡 ⑤ タイトル26〜28文字の厳密さ

前述の通り機械バリデータで担保します。加えて、SEO上は日本語タイトルは検索結果で28〜32文字程度で切れるため、この文字数指定は妥当です。

### 🟡 ⑥ 記事の一貫性（30〜50本/月のスケール）

同じ企業・同じテーマが月内に複数回登場します。過去に書いた記事との重複・矛盾を避けるため、**生成済み記事のインデックス**（タイトル・要旨・登場企業・使用データ）を蓄積し、新規記事生成時に参照させます。「＋α」の背景情報も、過去記事へ内部リンクを張ることでSEO効果が高まります。

## 付録A：他案（別AI提案）の評価

同じ相談を他の2つのAIにも投げた結果を突き合わせました。**両案ともNotionページの本文を取得できておらず、実際の要件（pptx納品、タイトル26〜28字、会員限定2/3、Canva3パターン、magnific、NNAが情報源であること）を知らない状態での一般論**です。そのうえで、設計として取り入れる価値のある指摘が4点ありました。

### 採用した4点（本レポートに反映済み）

| # | 指摘 | 反映先 | 採用理由 |
|---|---|---|---|
| 1 | Claude Code＝開発役／Claude API＝実行役／Python＝制御／VPS＝基盤 という役割分担の明示 | 3.4 | 「Claude Codeで完結」の意味が曖昧だったのは事実。ベンダーを増やさない話と、常駐プロセスの話は別なので分けて書くべき |
| 2 | Writer / Critic / Fact-Checker の役割分離（AI同士のチェック） | ③-b、4.1 | **最も価値のある指摘。** 同一コンテキストの自己点検は自分の出力に引きずられる。別コンテキストのレビュアーのほうが検出率が高い |
| 3 | 品質スコアによるトリアージ | 4.1 | 有用。ただし**公開可否の判断には使わず、チェック順序と注意箇所の提示に限定**する形に修正（AIの自己採点は甘く較正されていないため） |
| 4 | モジュール分割・完了通知・運用ログによる継続改善 | 4.2、5.1 | 実務的。特に「修正率を計測してプロンプトに反映する」は継続運用で効いてくる |

### 採用しなかった点と理由

| 指摘 | 判断 | 理由 |
|---|---|---|
| 画像生成API（`gpt-image-1` / DALL·E 3）の組み込みが必須 | **不採用** | 本件の成果物は**支給pptxテンプレートに沿った図表**であり、イラストではない。画像生成AIは日本語ラベルが崩れ、数値が実データと一致せず、pptx形式で納品できない。第2章参照 |
| PostgreSQL + Docker + APScheduler | **過剰** | 月50記事＝年600行。SQLiteで足りる。運用の複雑さが増えるだけ |
| Batch API による50%コスト削減 | **不採用** | リサーチ層がツール利用ループなのでバッチに乗らない。削減額は月$10程度で、24時間待ちに見合わない。プロンプトキャッシュを採用 |
| 「テーマ選定AIのほうが記事生成AIより重要」 | **対象外** | 本件はクライアントからNNA記事リンクが送られてくる。テーマ選定は業務範囲外 |
| 段階的に完全自動公開へ移行 | **保留** | 仕様書に「最終的な事実チェックと自然な文章になっているかは目視が必要」と明記されている。自社メディアの信頼性に直結するため、自動公開は目標に置かない。ただし「誤り率を計測する」という発想自体は 4.2 に採用 |
| 「独自の一次情報がないとSEO的に無価値」 | **既に充足** | 仕様書の「＋α」要件（イオンモールならこれまでのベトナム展開状況のまとめ等）がまさにこれに該当し、①リサーチ層で対応済み |

第三者の提案に含まれていた以下は、そのまま実装すると動きません。

- **`claude-3-5-sonnet` の指定** — 2025年10月に提供終了済みで、APIは404を返します。現行は `claude-opus-5` / `claude-sonnet-5` です

**NNA記事の二次利用が購読契約上許されるか**（リスク①）に、どちらも触れていません。これは本プロジェクトで唯一、技術で解決できない論点であり、パイプラインの入口設計（URL自動取得か、テキスト手動投入か）を左右します。Notionの本文を読めていれば必ず気づく箇所なので、情報の欠落が判断に直結した例と言えます。
